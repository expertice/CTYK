# Двухстороннее описание проекта CTYK (база для проектной документации)

## Как использовать этот документ

Этот документ представляет проект с двух сторон:
- Сторона A: продуктовая (зачем проект нужен бизнесу и пользователю).
- Сторона B: инженерная (как система устроена и работает технически).

Документ спроектирован как "исходник" для дальнейшей формализации:
- PRD/BRD (требования и бизнес-цели),
- SRS/Architecture docs (технические требования и архитектура),
- Runbook/Operations docs (эксплуатация и сопровождение),
- Quality/Test docs (стратегия тестирования).

---

## 1) Резюме проекта (Executive Summary)

`CTYK` (рабочее имя в коде и документации также встречается как `Transcribator`) — это платформа анализа рабочих аудиокоммуникаций, которая:
- принимает аудио из разных источников (локальный upload, URL, API, RTSP),
- выполняет распознавание речи (ASR) и диаризацию (speaker separation),
- обогащает результаты просодическим и rule-based анализом,
- запускает LLM-задачи (summary, deanon, narrative, checklist analysis),
- формирует итоговый отчет с возможностью PDF-экспорта.

Ключевой принцип продукта: пользователь собирает или выбирает сценарий (pipeline-граф из модулей), после чего запускает сессию и получает детальный результат по этапам обработки.

## 2) Сторона A: Продуктовое описание (Business / Product View)

## 2.1 Назначение и ценность

Проект решает задачу автоматизированного разбора рабочих разговоров и инструктажей, снижая ручные трудозатраты на:
- расшифровку аудио,
- разметку спикеров,
- интерпретацию контента,
- подготовку сводного аналитического отчета.

Бизнес-ценность формируется за счет:
- ускорения post-call/post-briefing аналитики,
- стандартизации качества анализа,
- масштабирования обработки без пропорционального роста команды аналитиков.

## 2.2 Целевой пользователь (предположительно)

По структуре сценариев и модулей, система ориентирована на роли типа:
- аналитик/оператор качества,
- руководитель смены/направления,
- специалист по аудиту коммуникаций.

Примечание: формализованный список persona/ICP в репозитории явно не найден и требует продуктовой валидации.

## 2.3 Основные пользовательские сценарии

1. Пользователь открывает конструктор сценариев или выбирает готовый сценарий.
2. Указывает источник аудио и параметры сессии.
3. Запускает обработку.
4. Следит за статусом выполнения модулей.
5. При необходимости вносит ручные правки speaker draft (human-in-the-loop этап).
6. Получает финальный `SESSION_REPORT` и экспорт в PDF.

## 2.4 Продуктовые артефакты/выходы

- Структурированный отчет по сессии (`SESSION_REPORT`).
- Данные по speaker turns и их нормализации.
- Результаты LLM-задач (summary/narrative/checklist и др.).
- PDF-документ для внешнего использования.

## 2.5 Границы продукта (на текущем этапе)

Система предоставляет end-to-end обработку внутри одного web-приложения и локального runtime.
Судя по коду, акцент сделан на рабочий MVP/операционный контур, а не на fully-managed enterprise-platform с продвинутой многозонной инфраструктурой.

## 3) Сторона B: Техническое описание (Engineering View)

## 3.1 Архитектурный стиль

- Монолитное приложение на `Next.js` (App Router), где:
  - UI,
  - API endpoints,
  - orchestration pipeline
  находятся в одном кодовом контуре (`apps/web`).

- Внутри бизнес-логики используется графовая pipeline-модель:
  - шаги (модули) соединяются ребрами по артефактам,
  - оркестратор запускает шаги пакетами с учетом зависимостей.

## 3.2 Ключевые подсистемы

1. **Scenario Builder**
   - управление графом модулей,
   - валидация совместимости связей и настроек.

2. **Pipeline Core**
   - контракты артефактов,
   - планирование последовательности выполнения,
   - логика pause/resume и human-gate.

3. **Processing Modules**
   - audio ingestion/preparation,
   - ASR,
   - diarization,
   - speaker merge/edit,
   - psych/prosody/rule-based модули,
   - LLM task modules,
   - report output module.

4. **LLM Integration Layer**
   - работа с OpenAI-compatible API,
   - provider/model resolution,
   - retry/timeout/fallback механики.

5. **Session/Job Runtime**
   - асинхронное выполнение через in-process очередь,
   - persisted state в файловой системе (`.runs-async`).

6. **Reporting**
   - сборка JSON-отчета,
   - PDF-генерация.

## 3.3 Технологический стек

- **Frontend/UI:** React 19 + Next.js 16 + TypeScript.
- **Backend/API:** Next.js Route Handlers (Node runtime).
- **AI/ML runtime (локально):** Python-интеграции для `faster-whisper`, `pyannote`, `librosa`, `ffmpeg`.
- **LLM:** OpenAI-compatible endpoint (локальный или облачный provider).
- **Report/PDF:** `pdf-lib`, markdown parsing (`marked`).
- **Storage:** файловая система (состояния/сценарии/uploads), явной внешней БД не обнаружено.

## 3.4 Основные технические точки входа

- UI:
  - `/`
  - `/sessions/new`
  - `/sessions/[id]`
  - `/sessions/[id]/status`
  - `/scenarios/build`

- Ключевые API группы:
  - `/api/pipeline/*`
  - `/api/jobs/*`
  - `/api/sessions/*`
  - `/api/scenarios/*`
  - `/api/runtime/*`
  - `/api/llm/*`
  - `/api/uploads/*`

## 3.5 Асинхронность и состояние

Модель выполнения:
- запуск пайплайна создает job/session,
- worker обрабатывает шаги и сохраняет прогресс на диск,
- UI/API читают статус и результаты из file-based state.

Плюсы:
- простота локального запуска и отладки,
- прозрачность артефактов на уровне файлов.

Ограничения:
- слабая горизонтальная масштабируемость,
- единичная точка отказа процесса/нод,
- необходимость явных стратегий backup/recovery.

## 4) Модель данных и артефактов (концептуально)

Ключевой доменный поток:
`Audio Source -> Prepared Audio -> ASR Transcript -> Diarization -> Speaker Turns -> Enriched Analysis -> LLM Outputs -> Session Report`

Основная единица обмена между модулями — артефактный контракт (envelope), который:
- описывает тип результата шага,
- передается по ребрам графа к следующим шагам,
- участвует в валидации совместимости модулей.

## 5) Операционный контур (Run / Build / Runtime)

Типовые команды:
- `pnpm dev`
- `pnpm build`
- `pnpm start`
- `pnpm lint`

Дополнительно:
- скрипты подготовки словарей/моделей (включая offline pyannote bundle).

Важные runtime-зависимости:
- Python,
- FFmpeg,
- (опционально) NVIDIA runtime для ускорения,
- HF token для отдельных сценариев загрузки/инициализации моделей.

## 6) Нефункциональные требования (черновой baseline)

Ниже требования, которые рекомендуется зафиксировать в формальной документации:

1. **Performance**
   - целевое время обработки на 1 час аудио,
   - допустимая очередь/конкурентность.

2. **Reliability**
   - правила восстановления после падения процесса,
   - корректность resume незавершенных job.

3. **Security**
   - хранение секретов (`apiKey`, токены),
   - политика доступа к API и чувствительным данным.

4. **Privacy/Compliance**
   - правила retention аудио/транскриптов,
   - обработка PII и журналирование доступа.

5. **Observability**
   - централизованные логи,
   - метрики пайплайна и ошибок,
   - алерты по деградациям/падениям.

---

## 7) Риски и пробелы текущей реализации

1. **Масштабирование**
   - in-process queue + file storage ограничивают multi-node scaling.

2. **Тестовая зрелость**
   - в кодовой базе не выявлен полноценный явный слой unit/integration/e2e тестов.

3. **Production governance**
   - не зафиксирован единый deploy/runbook (release strategy, rollback, DR).

4. **Артефактные контракты LLM**
   - есть признаки переходных/legacy участков, требующих унификации и стабилизации.

5. **Формализация продукта**
   - отсутствуют явные KPI/SLA/SLO и формальная продуктовая матрица сценариев.
